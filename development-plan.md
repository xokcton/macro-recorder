# План разработки: Macro Recorder/Player (Rust)

Кроссплатформенное приложение для записи и воспроизведения действий пользователя (клики, скроллы, клавиатура) с сохранением таймингов, паузой записи/воспроизведения, несколькими макросами, редактором шагов и трей-иконкой.

---

## 1. Технологический стек

| Слой | Выбор | Почему |
|---|---|---|
| Захват/симуляция ввода | `rdevin` (форк `rdev`, поддерживается активно, есть serde) | `rdev` от Narsil сам себя описывает как pet-проект и почти не развивается; `rdevin` — форк, который специально создан ради поддержки (его использует RustDesk), плюс из коробки есть `serde`-фичи под сериализацию событий |
| GUI | `egui` / `eframe` | Чистый Rust, без Node/WebView-зависимостей, единый тулчейн под все 3 ОС, immediate-mode UI хорошо подходит под редактор списка шагов |
| Трей-иконка | `tray-icon` | Стандартный крейт экосистемы tauri-apps, совместим с winit-циклом, на котором работает `eframe` |
| Глобальные хоткеи | `global-hotkey` | От той же команды, что и `tray-icon` — совместимость гарантирована |
| Сериализация | `serde` + `serde_json` | Человекочитаемый формат макроса, легко дебажить и версионировать |
| Хранение путей | `directories` | Кроссплатформенные пути к данным приложения (`%APPDATA%`, `~/Library/Application Support`, `~/.config`) |
| Ошибки | `thiserror` (core) + `anyhow` (app) | Типизированные ошибки в движке, гибкая обработка на верхнем уровне |
| Логирование | `tracing` + `tracing-subscriber` | Структурированные логи, важно для дебага проблем с таймингами на проде |
| Межпоточное взаимодействие | `crossbeam-channel` | Каналы между потоком записи/воспроизведения и UI-потоком |

**Важное техническое решение — Tauri не берём.** Он дал бы более гибкую вёрстку UI (HTML/CSS), но добавляет WebView2 (Windows) / WebKitGTK (Linux) как внешнюю зависимость и разрыв Rust↔JS через IPC. Для инструмента такого типа (немного экранов, много системных хуков) чистый Rust даёт более простую сборку, меньший бинарник и один язык на весь проект. Если позже понадобится богатый UI — миграция на Tauri возможна, т.к. core-крейт от UI не зависит (см. архитектуру).

## 2. Архитектура (Cargo workspace)

```
macro-recorder/

│       ├── player.rs          # Player: play/pause/resume/stop, циклы
│       ├── storage.rs         # save/load макросов на диск (JSON)
│       ├── hotkeys.rs         # обёртка над global-hotkey
│       └── error.rs           # CoreError (thiserror)
├── app/                       # исполняемый бинарник — GUI
│   └── src/
│       ├── main.rs
│       ├── state.rs           # AppState (Idle/Recording/Playing), Arc<Mutex<..>>
│       ├── ui/
│       │   ├── mod.rs
│       │   ├── main_window.rs # кнопки, статус, список макросов
│       │   ├── step_editor.rs # таблица шагов: ред-е, reorder, вставка/удаление
│       │   ├── settings.rs    # назначение хоткеев, скорость воспроизведения
│       │   └── tray.rs        # меню трея

├── assets/                    # иконки (idle/recording/playing) под трей и .app/.exe
└── .github/workflows/release.yml
```

Принцип: **`core` ничего не знает про UI**. Это даёт две вещи сразу:
- юнит-тесты движка без поднятия GUI;
- возможность позже добавить `cli/` (headless-запуск макроса по имени файла, полезно для CI/автоматизации) или другой фронтенд, не трогая логику.

## 3. Модель данных

```rust
pub enum InputEvent {
    MouseMove   { x: i32, y: i32 },
    MouseButton { button: MouseButton, pressed: bool },
    MouseWheel  { delta_x: i32, delta_y: i32 },
    Key         { key: Key, pressed: bool },
}

pub struct MacroStep {
    pub event: InputEvent,
    pub delay_ms: u64,   // задержка перед этим событием относительно предыдущего
}

pub enum LoopMode { Once, Times(u32), Infinite }

pub struct Macro {
    pub id: Uuid,
    pub name: String,
    pub steps: Vec<MacroStep>,
    pub loop_mode: LoopMode,
    pub created_at: DateTime<Utc>,
}
```

Формат хранения — один JSON-файл на макрос в папке данных приложения + `index.json` со списком (id, имя, дата) для быстрой загрузки списка без парсинга всех файлов.

## 4. Recorder — движок записи

- `rdevin::listen()` в отдельном потоке ловит глобальные события ОС.
- Каждое событие получает временную метку и добавляется в `Vec<MacroStep>` с `delay_ms = now - last_active_instant`.
- **Пауза записи** (твоё требование): пока запись на паузе, callback просто отбрасывает входящие события, хук не переустанавливается (это дороже и менее надёжно). При `resume()` происходит сброс `last_active_instant = Instant::now()` — значит время, проведённое на паузе, **не** попадает в тайминг следующего шага. Так пауза из-за долгого интернет-ответа не «зашивается» в сценарий.
- `stop()` останавливает поток и возвращает готовый `Macro`.

```rust
impl Recorder {
    pub fn start(&mut self) -> Result<(), CoreError>;
    pub fn pause(&mut self);
    pub fn resume(&mut self);
    pub fn stop(&mut self) -> Macro;
}
```

## 5. Player — движок воспроизведения

- Отдельный поток идёт по `Vec<MacroStep>`, перед каждым шагом «спит» `delay_ms` (с учётом множителя скорости из настроек) и вызывает `rdevin::simulate()`.
- **Ключевая деталь для устойчивости:** сон реализован не одним `thread::sleep(delay_ms)`, а циклом маленьких чанков по ~30–50 мс с проверкой флагов `paused` / `stopped` на каждой итерации. Это значит:
  - пауза/стоп по хоткею срабатывают почти мгновенно, даже если текущая задержка — несколько секунд;
  - **пауза воспроизведения** (второе твоё требование) блокирует поток на неопределённое время до `resume()` — то есть можно поставить макрос на паузу перед медленной загрузкой страницы, дождаться её вручную и продолжить точно с того же места, без пересборки сценария.
- Поддержка `LoopMode`: Once / Times(n) / Infinite (бесконечный останавливается только стоп-хоткеем).

```rust
impl Player {
    pub fn play(&mut self, macro_: Macro, speed: f32) -> Result<(), CoreError>;
    pub fn pause(&mut self);
    pub fn resume(&mut self);
    pub fn stop(&mut self);
}
```

## 6. Хоткеи и трей

- `global-hotkey` регистрирует комбинации из настроек (по умолчанию, например: `Ctrl+Alt+R` — старт/стоп записи, `Ctrl+Alt+P` — старт/стоп воспроизведения, `Ctrl+Alt+Space` — пауза/резюм текущего действия).
- Хоткеи отправляют события в общий канал, который слушает конечный автомат `AppState` (Idle / Recording{paused} / Playing{paused}) — одна точка принятия решений, что делать с нажатием, без раскиданной по UI логики.
- `tray-icon`: иконка отражает состояние (серая — Idle, красная точка — запись, зелёная — воспроизведение), контекстное меню — Показать окно / Воспроизвести последний макрос / Стоп / Выход.

---

## 7. UI (экраны, egui)

1. **Главное окно** — верхняя панель (Запись/Стоп, Играть/Пауза/Стоп, индикатор статуса и текущих таймингов), слева список макросов, справа — редактор шагов выбранного макроса.
2. **Редактор шагов** — таблица: № / тип события / параметры (x,y / клавиша / дельта скролла) / задержка (мс, редактируемая), кнопки вверх/вниз для reorder, вставка/удаление строки вручную.
3. **Настройки** — назначение хоткеев (запись комбинации нажатием), скорость воспроизведения (0.5x–3x), автосохранение при остановке записи, сворачивание в трей при закрытии окна.

---

## 8. Обработка ошибок, логирование

- `CoreError` (thiserror): `PermissionDenied`, `HookInitFailed`, `Io`, `Serialization`, `HotkeyConflict`.
- `tracing` пишет в файл в папке данных приложения (ротация по размеру) — критично для диагностики платформенных проблем у пользователя, которые сложно воспроизвести локально.
- UI никогда не паникует на ошибке движка — все `Result` доходят до слоя `commands.rs` и превращаются в toast/уведомление.

---

## 9. Тестирование

- **Core**: юнит-тесты на сериализацию, на арифметику таймингов (в т.ч. сценарий паузы — что delay после resume не включает время паузы), на конечный автомат Player/Recorder без реального `rdevin` (через trait-абстракцию над источником событий, чтобы подставлять мок в тестах).
- **UI**: ручное QA чек-листом на каждой ОС перед релизом (глобальные хуки плохо тестируются автоматически в CI-контейнерах без дисплея).
- `clippy` + `rustfmt` в CI как обязательный шаг.

## 10. Кроссплатформенные риски (важно знать заранее)

| ОС | Риск | Митигация |
|---|---|---|
| macOS | Нужны права Accessibility + Input Monitoring, выдаются вручную при первом запуске | Показать понятный экран-инструкцию при первом старте, если хук не поднялся |
| macOS | Неподписанное приложение → Gatekeeper ругается | На релиз — Developer ID подпись + нотаризация (отдельная задача, не блокирует MVP) |
| Linux | Глобальный хук на **чистом Wayland** работать не будет (ограничение безопасности компоситора) | На старте поддерживаем X11/XWayland-сессии; Wayland — через `evdev`+`uinput` как отдельная фаза после MVP |
| Windows | Симуляция ввода в окна, запущенные от администратора, требует, чтобы и наше приложение было elevated (UIPI) | Задокументировать в README, опционально — манифест с запросом повышения прав |
| Windows | Антивирус/SmartScreen может флагать automation-тулзы | Подпись бинарника сертификатом — вопрос уже готового к релизу продукта, не MVP |

**Рекомендация:** первым делом сделать технический спайк (0.5–1 день) — минимальный пример на `rdevin`: поймать клик и один раз его же воспроизвести на всех трёх ОС. Это самый рискованный узел архитектуры, и дешевле проверить его до того, как вокруг него построено всё остальное.

## 11. CI/CD и сборка

- GitHub Actions, матрица `windows-latest / macos-latest / ubuntu-latest`, на каждую — `cargo build --release`.
- Упаковка: `cargo-dist` — генерирует инсталляторы (`.msi`/`.exe` для Windows, `.dmg` для macOS, `.deb`/`AppImage` для Linux) и сразу собирает GitHub Release со всеми артефактами. Меньше ручной возни, чем городить `cargo-bundle`/`cargo-deb` по отдельности.
- Нативная сборка под каждую ОС именно на раннере этой ОС (кросс-компиляция GUI-приложений с системными хуками — источник лишних проблем, не стоит того).

## 13. За рамками MVP (задел на будущее)

Не делаем сейчас, но архитектура это не блокирует:
- Условные шаги / ожидание появления элемента по картинке (image recognition) — конкурент ручной паузы, но сложнее.
- Переменные и параметризация макроса (например, разный текст при каждом запуске).
- Планировщик запуска макросов по расписанию.
- Headless CLI-режим (`cli/` крейт) для запуска макроса без GUI, например по cron.
