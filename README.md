# Macro Recorder

Кроссплатформенный (Windows / Linux / macOS) рекордер и плеер макросов: записывает клики,
скроллы и клавиатуру с таймингами, умеет ставить запись/воспроизведение на паузу (не теряя
тайминг), опционально проверяет, что экран перед кликом не "уехал" (screen-guard), управляется
кнопками и глобальными хоткеями.

## Статус

Реально собрано, протестировано и проверено **вживую** (не только компилируется — см. раздел
"Что реально проверено" ниже):

- [x] `mrcore` — платформонезависимое ядро: запись, воспроизведение, тайминги, хранение
- [x] Пауза записи не "съедает" в тайминг время простоя (юнит-тесты + живой спайк)
- [x] Пауза воспроизведения — отзывчивая (реагирует за ~25мс, а не после текущей задержки)
- [x] Screen-guard: лёгкий perceptual-hash (без нейросетей) отпечаток экрана вокруг клика,
      авто-пауза + предупреждение при несовпадении — выключен по умолчанию, включается фичей
      `screen-guard` (см. ниже). Сохранение отпечатка и сохранение миниатюры-превью —
      независимые настройки
- [x] GUI на egui/eframe: кнопки записи/паузы/стопа, список сохранённых макросов, слайдер
      скорости воспроизведения
- [x] Глобальные хоткеи (Ctrl+Alt+R / Ctrl+Alt+P / Ctrl+Alt+Space / Ctrl+Alt+Escape) —
      **редактируются прямо в UI** (⚙ Настройки → Хоткеи), с проверкой конфликтов и
      персистентностью между запусками; по умолчанию требуют модификатор, но это тоже настройка
- [x] Сохранение макросов на диск (JSON, по одному файлу на макрос) + индекс-файл со сводками:
      список в UI читается из лёгкого кэша; тела макросов (с превью) грузятся только по ▶/✏;
      запись атомарная (tmp + rename)
- [x] Трей-иконка (показать окно / играть последний макрос / стоп / выход), цвет отражает
      статус (серый/красный/зелёный) — **опционально**, фича `tray` (включена по умолчанию,
      см. "Сборка")
- [x] Редактор шагов: правка задержки каждого шага, **drag&drop reorder мышью**, удаление
      шага, переименование макроса
- [x] Явный выбор макроса в списке (клик по строке) — им управляют хоткей/трей "играть";
      обычный клик "▶" тоже выбирает, так что поведение предсказуемо в обоих случаях
- [x] Превью экрана в редакторе шагов — маленькая миниатюра рядом с шагом, у которого
      сохранена миниатюра (отдельно от отпечатка для сверки при воспроизведении — см. выше).
      **О приватности**: это настоящий, хоть и маленький (32×32), фрагмент экрана — при
      экспорте/синхронизации макроса он уедет вместе с файлом (подробнее — "Известные
      ограничения")
- [x] Настройки (язык + хоткеи + экран-сторож) сохраняются между запусками — один JSON-файл,
      см. "Настройки"
- [x] Упаковка в инсталляторы через `dist` (бывший `cargo-dist`): shell-инсталлятор для
      Linux/macOS, MSI + PowerShell-инсталлятор для Windows — `.github/workflows/release.yml`
      генерируется автоматически, публикует GitHub Release при пуше тега `v*`
- [x] Локализация (русский/английский), переключатель прямо в UI — переводы обычным JSON,
      новый язык добавляется без изменений в остальном коде (см. "Локализация")
- [x] Боковые/средняя кнопки мыши на macOS — исправлено патчем поверх `rdevin` (см.
      "Известные ограничения": **не проверено на реальном Mac**, только по исходникам)
- [x] Режимы повтора макроса: один раз / N раз / бесконечно — выбор в редакторе шагов,
      старые файлы макросов полностью совместимы
- [x] Коалесинг движений мыши при записи: секундное перемещение — один шаг вместо сотен;
      удержания клавиш опционально сжимаются настройкой в параметрах
- [x] Мгновенная реакция на глобальные хоткеи (событийная модель, нулевой CPU в простое);
      нажатия во время захвата новой комбинации не «доигрываются» после
- [x] Предупреждение прямо в окне, если захват ввода недоступен (типично — Wayland),
      с указанием причины и подсказкой, что делать (см. "Известные ограничения")
- [x] CLI-проигрыватель `mrec` — headless-запуск макроса из файла (см. раздел «CLI»)
- [x] Экспериментальный бэкенд ввода `evdev`+`uinput` для чистого Wayland — запись из
      `/dev/input/*` и воспроизведение через виртуальное устройство `/dev/uinput`, минуя
      протокол Wayland целиком (фича `evdev`, только Linux). Переключается в ⚙ Настройки →
      Ввод и в CLI флагом `mrec play --backend evdev`. **Компилируется, покрыто юнит-тестами
      и проходит clippy в CI — но не проверялось вживую на реальном Wayland-компоситоре**
      (подробности и что стоит проверить руками — см. "Известные ограничения")
- [x] Глобальные хоткеи на чистом Wayland через `org.freedesktop.portal.GlobalShortcuts`
      (фича `portal-hotkeys`) — включается автоматически, если обычный перехват хоткеев не
      смог зарегистрироваться. **Тоже не проверено на реальном композиторе** — см. ниже

## Сборка

```bash
cargo build --release
# бинарник: target/release/macro-recorder (или .exe на Windows)
```

Без трея (не тянет GTK на Linux вообще — самая тяжёлая платформенная зависимость в проекте):

```bash
cargo build --release --no-default-features
```

Опционально — со screen-guard (см. "Известные ограничения" про его вес):

```bash
cargo build --release --features screen-guard
```

Опционально — с экспериментальной поддержкой чистого Wayland (только Linux, см. "Известные
ограничения" — не проверено на реальном композиторе):

```bash
cargo build --release --features evdev,portal-hotkeys
```

`evdev` даёт бэкенд записи/воспроизведения через `/dev/input`+`/dev/uinput`, `portal-hotkeys` —
глобальные хоткеи через `org.freedesktop.portal.GlobalShortcuts`. Их можно включать по
отдельности: `evdev` полезен и сам по себе (запись/воспроизведение), `portal-hotkeys` без
`evdev` тоже имеет смысл (например, на X11/XWayland, где запись работает через rdevin, а хоткеи
всё равно хочется брать через портал). У `mrec` (CLI) своя фича `evdev`, форвардящая в
`mrcore/evdev` — `cargo build --release -p macro-recorder-cli --features evdev`, флаг
`--backend evdev` (см. "CLI").

Все фичи независимы и комбинируются как угодно.

> Фича `screen-guard` — на `app`, а не только на `mrcore`: `app/Cargo.toml` объявляет свою
> `screen-guard`, которая сама форвардит в `mrcore/screen-guard` (см. `app/src/screen_guard.rs`).
> Раньше (до текущей сессии) `--features mrcore/screen-guard` включал реализацию только внутри
> ядра, а само приложение `XcapScreenGuard` нигде не создавало — фича физически ничего не давала
> в собранном бинарнике. Если где-то в старых заметках/скриптах встретится
> `--features mrcore/screen-guard` — замените на `--features screen-guard`.

> Про папку `vendor/rdevin-0.1.0/`: это не "лишний" код — это патченая копия крейта `rdevin`
> с фиксом боковых кнопок мыши на macOS, подключённая через `[patch.crates-io]` в корневом
> `Cargo.toml`. Подробности и статус проверки — `vendor/rdevin-0.1.0/README-PATCH.md`.

### Linux: системные зависимости

```bash
sudo apt install libx11-dev libxtst-dev libxi-dev libxext-dev   # обязательно
sudo apt install libgtk-3-dev libxcb-render0-dev libxcb-shape0-dev libxcb-xfixes0-dev \
  libxkbcommon-dev                                            # только для фичи tray
```

Для фичи `evdev` дополнительных `-dev`-пакетов не нужно (крейт `evdev` тянет только
`libc`/`nix`, без `libudev`), но нужны **права на уровне устройств**, а не пакеты:

```bash
sudo usermod -aG input $USER   # затем перелогиниться (или `newgrp input`)
```

Этого обычно достаточно для *чтения* `/dev/input/event*` (запись макроса). Для *записи* в
`/dev/uinput` (воспроизведение через виртуальное устройство) группы `input` может не хватить —
на некоторых дистрибутивах узел `/dev/uinput` по умолчанию `root:root 0600`. Если после
`usermod` воспроизведение всё равно падает с "Permission denied", нужно явное udev-правило,
например:

```bash
echo 'KERNEL=="uinput", GROUP="input", MODE="0660"' | sudo tee /etc/udev/rules.d/99-uinput.rules
sudo udevadm control --reload-rules && sudo udevadm trigger
```

**Это не проверялось на реальном дистрибутиве в этой сессии** — команды выше стандартны для
uinput в общем (не специфичны для этого проекта), но перед тем как полагаться на них, стоит
проверить `mrec play test.json --backend evdev` вживую и, если понадобится своё правило,
поправить этот раздел под конкретный дистрибутив. Фича `portal-hotkeys` (крейт `ashpd`/`zbus`,
чистый Rust, без `libdbus-dev`) дополнительных системных пакетов не требует вовсе — только
работающая сессионная шина D-Bus, которая на десктопе есть почти всегда.

### Упаковка в инсталляторы

Проект настроен на [`dist`](https://opensource.axo.dev/cargo-dist/) (бывший `cargo-dist`).
Локально (для той платформы, на которой собираете):

```bash
cargo install cargo-dist --locked   # один раз
dist build --artifacts=local
# результат: target/distrib/*.tar.xz (+ .sha256), на Windows дополнительно .msi
```

Реальный релиз под все три ОС делает `.github/workflows/release.yml` (уже сгенерирован) —
он запускается на push тега вида `v0.1.0` и публикует GitHub Release с инсталляторами,
собранными на нативных runner'ах каждой ОС (сборка под Windows/macOS кросс-компиляцией
не производится — только на настоящих раннерах, это осознанный выбор, см. план разработки).
Конфигурация — в `dist-workspace.toml` и `[profile.dist]` в корневом `Cargo.toml`.

**Проверено локально в этой сессии**: `dist build --artifacts=local --target
x86_64-unknown-linux-gnu` — полный прогон, включая сборку релизного профиля (LTO) и
упаковку — реально выполнен от начала до конца, архив распакован, бинарник запущен и
проверен под Xvfb, контрольная сумма сошлась. Windows (`.msi` через WiX,
конфиг сгенерирован в `app/wix/main.wxs`) и macOS не собирались вживую — на native
раннере GitHub Actions должны собраться по тому же пайплайну без дополнительных правок,
но стоит проверить при первом релизе.

### Тесты

```bash
cargo test --workspace
```

88 тестов: 67 в `mrcore`, 15 в `macro-recorder-app` (i18n, drag&drop-логика, форматирование
длительности), 6 в `macro-recorder-cli` (парсер аргументов, включая `--backend`) — всё юнит-/
интеграционные, используют `MockBackend`/`MockScreenGuard`/временные директории, реальную ОС не
трогают, безопасно гонять в CI без дисплея. Числа соответствуют фактическому прогону
`cargo test --workspace` (67 + 15 + 6), включая CI на трёх ОС.

Отдельно, только под своими фичами (не входят в число выше — CI гоняет их дополнительным шагом
только на Linux, см. `.github/workflows/ci.yml`):

```bash
cargo test -p mrcore --features evdev --lib                       # +14: маппинги кодов клавиш/
                                                                    #  кнопок evdev↔домен, симуляция
cargo test -p macro-recorder-app --features evdev,portal-hotkeys  # +2: перевод комбинаций в
                                                                    #  формат портала и обратно
```

Эти тесты — чистая логика (таблицы соответствий, сериализация), без реального `/dev/input`,
`/dev/uinput` или D-Bus-портала: сеть/устройства/desktop-сессия для них не нужны, поэтому они
безопасны в CI. Но именно поэтому они и не заменяют ручную проверку на живом Wayland — см.
"Известные ограничения".

## CLI

Без GUI, для скриптов и автоматизации:

```bash
mrec play ~/.local/share/macro-recorder/macros/<uuid>.json
mrec play login.json --speed 2.0 --times 5   # быстрее, ровно 5 проходов
mrec play loop.json --forever                # бесконечно, остановка — Ctrl-C
mrec play loop.json --backend evdev          # чистый Wayland: симуляция через /dev/uinput
                                              # (нужна сборка --features evdev, см. "Сборка")
```

По умолчанию `--backend rdevin` — тот же способ ввода, что и у GUI без флагов. На чистом
Wayland `rdevin` не сможет ничего воспроизвести; `mrec` определяет это по `WAYLAND_DISPLAY`/
`XDG_SESSION_TYPE` и печатает предупреждение в stderr с подсказкой попробовать
`--backend evdev` — но не переключается автоматически (осознанный выбор: headless-сценарии
скриптуются, и молчаливая смена бэкенда посреди автоматизации может удивить сильнее, чем явная
ошибка). См. "Известные ограничения" — этот путь не проверялся на реальном Wayland.

## Локализация

Переводы — обычный JSON (`app/i18n/ru.json`, `app/i18n/en.json`), вшитый в бинарник на этапе
компиляции. Переключатель языка — прямо в UI (сверху окна).

**Чтобы добавить новый язык:**

1. Скопировать `app/i18n/en.json` в `app/i18n/<code>.json`, перевести значения (ключи не трогать).
2. Добавить один элемент в массив `LANGS` в `app/src/i18n.rs`.
3. Пересобрать.

Всё остальное — переключатель в UI, подстановка параметров вида `{0}`/`{1}` в переведённые
строки — работает автоматически; экраны (`app.rs`, `step_editor.rs`, `tray.rs`) ничего не знают
про список языков. Тест `i18n::tests::every_key_in_default_language_exists_in_all_others`
проверяет, что во всех `*.json` один и тот же набор ключей — забытый перевод при добавлении
языка будет падением теста, а не молча пустой строкой в UI.

## Что реально проверено (не только "должно работать")

Всё ниже проверялось вручную в контейнере под Xvfb (виртуальный X11-дисплей) с реальным
`rdevin` — не моками:

1. **Запись реально ловит события ОС.** `cargo run -p mrcore --example spike_record` +
   синтетический ввод через `xdotool` → корректно захвачены клики, клавиши, движения мыши.
2. **Воспроизведение реально доходит до ОС.** `cargo run -p mrcore --example spike_playback`,
   события которого поймал независимый слушатель (наш же `listen()`) — то есть цикл
   запись→воспроизведение замкнут и работает по-настоящему на живом X11.
3. **Боковые кнопки мыши (Button4/5, "вперёд/назад") записываются и воспроизводятся на Linux и
   Windows** — подтверждено и по исходникам `rdevin`, и вживую (X11 button 8 корректно
   прошёл через весь пайплайн в примере выше). **На macOS изначальная версия `rdevin` их не
   ловила вообще**; в проекте это исправлено патчем поверх векторизованной копии `rdevin`
   (`vendor/rdevin-0.1.0/`, см. "Известные ограничения") — но сам патч, в отличие от всего
   остального в этом разделе, **не проверен на реальном Mac**, только по исходникам
   `core-graphics`.
4. **Приложение реально открывает окно и рисует UI** под Xvfb — скриншотами подтверждён переход
   между состояниями (запись → пауза → стоп) как по кнопкам, так и по глобальным хоткеям.
5. **Трей-иконка инициализируется и не роняет приложение** под Xvfb + реальным D-Bus session
   bus (`dbus-launch`) — GTK/`libappindicator` поднимаются, опрос GTK-очереди на каждый кадр не
   блокирует основной цикл (окно продолжает реагировать на хоткеи, пока трей активен). Реальный
   клик по иконке в системном лотке не проверялся — в headless-песочнице нет хоста трея
   (StatusNotifierWatcher), только визуальная панель задач может это принять.
6. **Редактор шагов проверен объективно, не на глаз**: макрос засеян напрямую через `Storage`,
   открыт в UI (клавиатурная навигация Tab + Space — по факту то же самое, что клик мышью,
   egui обрабатывает это одинаково), нажата "Сохранить" — после этого **на диске реально
   обновился mtime файла и его содержимое** осталось валидным JSON с теми же 8 шагами.
7. **Упаковка в инсталлятор реально запускалась до конца**: `dist build --artifacts=local`
   собрал релизный (LTO) бинарник, запаковал в `.tar.xz` с корректной `.sha256`, бинарник из
   архива запущен и работает.
8. **Локализация реально переключается в работающем приложении**: скриншот на русском и на
   английском после клика по переключателю объективно отличаются (попиксельное сравнение,
   не "на глаз") в области статуса и заголовков разделов.
9. **Сборка без фичи `tray` реально пропускает всю GTK-цепочку**: `cargo check
--no-default-features` укладывается в секунды вместо минут и не тянет
   `gtk`/`libappindicator`/`zbus` — то, ради чего фича вообще вынесена отдельно.
10. **Перепривязка хоткея проверена end-to-end, объективно, без единого "на глаз".**
    Сценарий: захват новой комбинации (`Ctrl+Shift+T`) через клавиатурный ввод → проверено,
    что `settings.json` на диске обновился → **перезапущено** приложение (реально загрузило
    привязку с диска) → `Ctrl+Shift+T` реально запускает запись → а **старая** `Ctrl+Alt+R`
    после перепривязки уже ничего не делает (скриншот до/после нажатия — побитово идентичен,
    т.е. `unregister()` старой комбинации действительно сработал, а не просто переехал в
    UI-состоянии).
11. **Настройки языка реально сохраняются и переживают перезапуск**: переключение на English
    в UI → `settings.json` на диске содержит `"language": "en"` сразу после переключения, без
    дополнительных действий.
12. **Превью экрана в редакторе шагов реально рисуется правильным содержимым, не просто
    "что-то появилось".** Засеян макрос с синтетическим отпечатком+миниатюрой заведомо
    известного цвета (бирюзовый `rgb(0,200,180)`) → редактор открыт → на скриншоте окна
    попиксельным поиском найдено 784 пикселя этого точного цвета, образующих компактную
    область 27×27px ровно там, где должна быть миниатюра нужного шага. Это проверяет всю
    цепочку целиком: base64 из JSON → декодирование → `ColorImage` → текстура GPU → `ui.image`.

**Проверено менее строго** (компиляция + `clippy` + ручной прогон в Xvfb без падений, но без
отдельного объективного теста уровня пункта 10 выше): явный выбор макроса кликом по строке
списка и drag&drop reorder шагов в редакторе. Код в обоих случаях следует тем же простым,
уже проверенным паттернам (`to_select`/`to_play`/`to_edit`, `move_item` — юнит-тестами покрыт
отдельно), но полного end-to-end сценария с объективной проверкой результата (как для
хоткеев/настроек выше) для них не гонялось.

Чего **не** проверено (нет macOS/Windows под рукой в этой среде): поведение на самих Windows и
macOS, включая сборку `.msi`/PowerShell-инсталлятора. Архитектурно код должен работать
одинаково (вся платформенная специфика — внутри `rdevin`/`tray-icon`/`global-hotkey`, каждая
из которых сама поддерживает три ОС), но первое, что стоит сделать на реальной машине —
прогнать те же примеры-спайки и `dist build`.

Отдельно, и это важнее для чистого Wayland (см. "Известные ограничения"): бэкенд `evdev`,
воспроизведение через `uinput` и портальные хоткеи (`GlobalShortcuts`) **не проверялись вживую
вообще ни разу** — ни в этой сессии, ни в предыдущих. Всё, что за них говорит, — компиляция,
`clippy` и юнит-тесты над чистой логикой (маппинг кодов, перевод комбинаций); ни доступа к
`/dev/input`/`/dev/uinput`, ни настоящего Wayland-композитора, ни рабочей сессионной D-Bus-шины
с портал-демоном в этой headless-песочнице не было. Это принципиально более слабый уровень
проверки, чем у всего остального в этом разделе — относитесь к пункту "evdev/uinput/portal" в
статусе выше как к "должно работать по коду", а не как к "проверено", пока кто-то не прогонит
`spike_evdev`/`spike_evdev_play` и саму GUI/CLI на реальном GNOME или KDE под Wayland.

## Ранние изменения (первоначально написаны ИИ-сессией без компилятора — с тех пор проверены)

Два пункта, которые раньше были в разделе "Возможные доработки" ниже, в этом заходе
реализованы:

- **Хоткей без модификатора — теперь настраивается.** Новый чекбокс в ⚙ Настройки → Хоткеи
  (`Settings::allow_bare_hotkeys`, по умолчанию выключен) снимает при захвате новой комбинации
  требование хотя бы одного модификатора (`app::settings_panel::capture_combo`). `Escape` без
  модификаторов по-прежнему всегда означает "отмена захвата" независимо от этой настройки —
  иначе отменить сам процесс захвата было бы нечем.
- **Screen-guard: отпечаток и миниатюра стали независимыми настройками.** Новый
  `mrcore::ScreenCaptureConfig { fingerprint, thumbnail }` (оба по умолчанию `false`) — вместо
  жёсткой пары. Применяется на лету, без перезапуска приложения (`Recorder::set_capture_config`,
  `Player::set_screen_guard`) — см. новый блок ⚙ Настройки → Экран-сторож. Попутно выяснилось,
  что `app.rs` до этой сессии вообще не создавал `XcapScreenGuard` — фича `screen-guard` у
  `mrcore` компилировалась, но реально ни на что не влияла в собранном приложении. Теперь у
  `app` своя фича `screen-guard` (форвардит в `mrcore/screen-guard`, см. новый
  `app/src/screen_guard.rs` и раздел "Сборка" — команда сборки поменялась). Заодно исправлен
  сопутствующий баг в `step_editor.rs`: превью миниатюры в редакторе шагов было завязано на
  наличие отпечатка (использовался как ключ кэша GPU-текстур) — при миниатюре без отпечатка
  превью просто не появилось бы; ключ кэша теперь считается по содержимому самой миниатюры.

**Актуальный статус обоих пунктов**: с момента написания они многократно прошли полный цикл —
`cargo fmt`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`
— локально и в CI на всех трёх ОС. Поведение покрыто юнит-тестами: roundtrip и деградация до
дефолтов для `allow_bare_hotkeys` (`core/src/settings.rs`), независимость и дефолты флагов
`ScreenCaptureConfig` (`core/src/screen_guard/mod.rs`).

## Известные ограничения

- **macOS: патч боковых кнопок мыши не проверен на реальном железе.** Код исправления
  (`vendor/rdevin-0.1.0/`, подробности в `README-PATCH.md` там же) написан по построчной сверке
  с исходниками `core-graphics` 0.22.3, но в среде разработки нет macOS — компилятор ни разу не
  видел эти конкретные строки на реальном таргете. Перед тем как полагаться на это в проде,
  стоит прогнать `cargo run -p mrcore --example spike_record` на настоящем Mac и покликать
  боковыми кнопками.
- **Screen-guard (`xcap`) — теперь реально собирается, и (с этой сессии) реально подключён к
  приложению.** Изначально в этой песочнице не собирался из-за старого системного Cargo (см.
  историю коммитов), но после того, как песочница сама обновила Rust до 1.91, `cargo check -p
mrcore --features screen-guard` проходит чисто. До этой сессии, впрочем, `app.rs` вообще не
  создавал `XcapScreenGuard` — фича влияла только на то, что компилируется внутри `mrcore`, но
  не на поведение собранного приложения; это исправлено (см. "Изменения в этой сессии" выше).
  Сама фича (запись реального отпечатка через `XcapScreenGuard`) на настоящем экране здесь не
  гонялась (headless-песочница, к тому же в этой сессии не было и самого Rust-тулчейна), но
  модуль хэша/сравнения — чистая арифметика, полностью покрыт тестами, а миниатюры для превью в
  редакторе шагов (см. следующий пункт) проверены end-to-end реальным рендерингом.
- **Приватность миниатюр screen-guard.** `ScreenThumbnail` (`core/src/screen_guard/mod.rs`) —
  это настоящий, хоть и маленький (32×32 по умолчанию, `DEFAULT_THUMBNAIL_SIZE`) фрагмент
  экрана вокруг места клика, сохранённый прямо в JSON-файле макроса base64-строкой. Если файл
  макроса кому-то передать, выложить в публичный репозиторий или синхронизировать в облако —
  эти фрагменты уедут вместе с ним. Риск ограничен (маленькая область только вокруг кликов, не
  весь экран), но не нулевой — там может быть виден текст кнопки, часть текстового поля и т.п.
  С этой сессии сохранение миниатюр — отдельная настройка (`ScreenCaptureConfig::thumbnail`,
  ⚙ Настройки → Экран-сторож), независимая от самой защиты от "уехавшего" интерфейса
  (`ScreenCaptureConfig::fingerprint`): можно держать автопаузу включённой, вообще не сохраняя
  фрагментов экрана на диск. По умолчанию оба флага выключены.
- **Трей на Linux, если фича `tray` включена (по умолчанию), тянет GTK/`libappindicator`** и
  приложение само прокачивает GTK event loop на каждый кадр (`app/src/tray.rs`, модуль `imp`,
  см. комментарий там же про то, почему это вообще нужно). Работает и не блокирует основной цикл
  (проверено). Если GTK на машине совсем не нужен — `cargo build --no-default-features`.
- **На чистом Wayland штатный ввод (`rdevin`) не работает** (ограничение безопасности
  компоситора — обычному приложению не дают ни слушать, ни синтезировать глобальные события
  ввода в обход портала). Приложение само это обнаруживает и показывает предупреждение прямо в
  окне, с текстом ошибки и подсказкой, что делать. Раньше единственным выходом было "используйте
  X11/XWayland"; теперь есть два пути, оба экспериментальные:
  - **Бэкенд `evdev`+`uinput`** (`core/src/backend/evdev_backend.rs`, фича `evdev`, только
    Linux) — запись читает события напрямую из `/dev/input/event*`, воспроизведение создаёт
    виртуальное устройство через `/dev/uinput` и синтезирует ввод на уровне ядра, в обход
    Wayland-протокола целиком. Переключается в ⚙ Настройки → Ввод (там же подсказка про
    Wayland) или флагом `mrec play --backend evdev` в CLI. Нужна сборка с `--features evdev` и
    доступ к устройствам — обычно группа `input`, но для `/dev/uinput` на части дистрибутивов
    нужно ещё и отдельное udev-правило (см. "Сборка" → "Linux: системные зависимости", там
    команды). Если бэкенд уже переключён на evdev, а ошибка всё равно есть — это почти всегда
    как раз про эти права, а не про Wayland как таковой (баннер в приложении различает два
    случая и подсказывает разное).
  - **Глобальные хоткеи через `org.freedesktop.portal.GlobalShortcuts`**
    (`app/src/portal_hotkeys.rs`, фича `portal-hotkeys`) — хоткеи (запись/пауза/стоп/играть)
    регистрируются через системный портал вместо прямого перехвата. Включается автоматически,
    если обычная регистрация хоткеев не удалась. Требует композитор с поддержкой этого портала
    (GNOME ≥ 43, KDE Plasma ≥ 6; часть wlroots-оболочек до сих пор его не реализует) — на
    остальных хоткеи на Wayland по-прежнему не будут работать вовсе, и это ожидаемо.

  **Важно — уровень проверки здесь другой, чем у всего остального в README.** Код компилируется,
  проходит `clippy -D warnings` и покрыт юнит-тестами на чистую логику (маппинг кодов клавиш
  evdev↔домен, перевод комбинаций в формат портала — 16 тестов, полный список в "Тесты"), CI
  гоняет это на каждый пуш. Но **ни один из этих путей ни разу не запускался на настоящем
  Wayland-компоситоре** — в песочнице, где это писалось, не было ни самого Wayland, ни прав на
  `/dev/input`/`/dev/uinput`, ни рабочего портал-демона. То есть не проверено: реально ли
  открывается `/dev/uinput` и создаётся виртуальное устройство, действительно ли композитор
  выдаёт клики/движения как настоящие (не только как заранее подготовленные тестами данные),
  и как на практике выглядит диалог согласия `GlobalShortcuts` (он у пользователя может
  потребовать явного разрешения при первом запуске — в коде это не эмулировано и не
  протестировано). Прежде чем полагаться на это в проде — прогоните `cargo run -p mrcore
  --features evdev --example spike_evdev` и `spike_evdev_play`, затем само приложение и `mrec`
  под реальной Wayland-сессией.

## Настройки

Один JSON-файл (`settings.json` в той же директории данных, что и макросы) хранит:

- **Хоткеи** — редактируются в ⚙ Настройки → Хоткеи: кнопка "Изменить" → нажать нужную
  комбинацию (по умолчанию нужен хотя бы один модификатор Ctrl/Alt/Shift — глобальный хоткей без
  модификатора перехватывал бы обычный ввод везде в системе; чекбокс "Разрешить хоткей без
  модификатора" под заголовком снимает это ограничение для продвинутых пользователей,
  `Settings::allow_bare_hotkeys`, по умолчанию выключен) → `Esc` отменяет захват (всегда, даже
  если голые хоткеи разрешены). Конфликт с уже занятой комбинацией показывается прямо в UI, старая
  привязка при этом не ломается.
- **Язык** — переключается там же, сохраняется сразу при переключении.
- **Экран-сторож** (⚙ Настройки → Экран-сторож, видно только если приложение собрано с фичей
  `screen-guard`, см. "Сборка") — два независимых чекбокса: сохранять отпечаток для проверки
  экрана перед кликом при воспроизведении, и отдельно — сохранять миниатюру-превью для
  редактора шагов (`Settings::screen_capture`, оба флага по умолчанию выключены). Меняются "на
  лету", без перезапуска приложения.

Настройки по умолчанию (если файла ещё нет):

| Комбинация        | Действие                                                               |
| ----------------- | ---------------------------------------------------------------------- |
| `Ctrl+Alt+R`      | Начать / остановить запись                                             |
| `Ctrl+Alt+Space`  | Пауза/продолжить (то, что сейчас активно — запись или воспроизведение) |
| `Ctrl+Alt+P`      | Играть выбранный макрос / остановить                                   |
| `Ctrl+Alt+Escape` | Аварийный стоп всего                                                   |

Заданы в `core/src/hotkeys.rs::default_bindings()`. Загрузка настроек (`core/src/settings.rs`)
никогда не роняет запуск приложения — отсутствующий, повреждённый или неполный (от старой
версии) файл просто заменяется значениями по умолчанию для недостающих полей.

## История разработки

Код развивался серией маленьких проверяемых правок: каждая итерация закрывала
конкретный дефект или добавляла возможность и сопровождалась юнит-тестами
(`cargo test --workspace`), а также обязательными `cargo fmt` и
`cargo clippy --workspace --all-targets -- -D warnings`.

### Основные итерации

1. **Плеер без лишних копий** — шаги воспроизводятся по ссылке вместо клона
   каждого шага на каждой итерации цикла: превью-скриншоты больше не
   дублируются при каждом проигрывании.
2. **Защитные фиксы движка**:
   - пустой макрос с бесконечным повтором больше не крутит холостой цикл под
     100 % CPU — проверка живёт в `Player::play`, и поток для пустого макроса
     вообще не создаётся;
   - устранена гонка рекордера: клик, «зависший» в захвате экрана на момент
     остановки записи, не протекает в следующую запись (повторная проверка
     после возврата лока).
3. **Атомарная запись файлов** — макросы и настройки пишутся во временный
   файл с `sync_all` и последующим переименованием: обрыв питания не оставит
   битый JSON; ошибки записи пробрасываются, а не глотаются.
4. **Коалесинг движений мыши** — подряд идущие `MouseMove` схлопываются в
   один шаг (последняя позиция + суммарная задержка): секундное движение —
   один шаг вместо сотен. Макросы компактнее, воспроизведение плавнее.
5. **Авто-повтор клавиш** — удержания распознаются по потоку повторных
   нажатий одной зажатой клавиши; опционально сжимаются в один шаг
   с суммарной задержкой (настройка в UI, по умолчанию выключена — повторы
   записываются «как есть»).
6. **`Arc<Macro>` до самого потока** — список макросов хранится в `Arc`,
   запуск ▶ не делает глубокую копию шагов и скриншотов; скорость
   воспроизведения страхуется от нулевого значения.
7. **Счётчик поколений записи** — закрывает редкую гонку «stop + start успели
   выполниться, пока колбэк снимал экран»: осиротевший клик не попадёт
   в новую запись (регрессионный тест с медленным моком захвата на барьере).
8. **События вместо опроса** — глобальные хоткеи (и меню трея на
   Windows/macOS) вычитываются фоновыми потоками в канал приложения
   с `request_repaint()`: реакция на хоткей мгновенная, в простое CPU ≈ 0 %.
   На Linux трей по-прежнему обслуживается в GUI-потоке (прокачка GTK-очереди),
   там сохранён лёгкий периодический тик. Нажатия хоткеев во время захвата
   новой комбинации выбрасываются — после захвата ничего не «доигрывается».
9. **Баннер о недоступности захвата ввода** — если системный слушатель
   событий не смог запуститься (типичный случай — Wayland), приложение
   сообщает об этом прямо в окне с указанием причины, а не делает вид,
   что «запись идёт».
10. **Режимы повтора в редакторе** — выбор «один раз / несколько раз (N) /
    бесконечно» рядом со списком шагов; поле `loop_mode` сериализуется
    с `#[serde(default)]`, старые файлы макросов полностью совместимы.
11. **Экспериментальная поддержка чистого Wayland** — второй бэкенд ввода,
    `EvdevBackend` (запись из `/dev/input/*`, воспроизведение через
    виртуальное устройство `/dev/uinput`), выбирается в настройках рядом с
    `RdevinBackend` (`Settings::input_backend`, фича `evdev`, только Linux) и
    полностью протестирован на уровне маппинга кодов клавиш/кнопок (14
    юнит-тестов, включая биекцию домен↔evdev). Глобальные хоткеи на Wayland —
    через `org.freedesktop.portal.GlobalShortcuts` (фича `portal-hotkeys`),
    подключаются автоматически, если обычный перехват хоткеев не смог
    зарегистрироваться (`app::portal_hotkeys`, 2 юнит-теста на перевод
    комбинаций в формат портала). CLI (`mrec`) получил флаг `--backend
    evdev` для headless-воспроизведения без X11. **В отличие от всего
    остального в этом списке — ни разу не запускалось на реальном
    Wayland-компоситоре**: только `cargo test`/`cargo clippy` в CI, без
    доступа к `/dev/input`, `/dev/uinput` или D-Bus-сессии портала (headless-
    песочница). Подробности и что нужно проверить перед тем, как полагаться
    на это в проде — см. "Известные ограничения".

### Полировка

- Длительность показывается по-человечески: `125000 мс` → `2:05`
  (часы — как `1:02:05`), и в списке макросов, и в шапке редактора.
- Редактор шагов (✏) доступен во время чужого воспроизведения; панель
  пауза/стоп при этом остаётся на виду.
- Подстановка плейсхолдеров `{0}`…`{n}` в переводах выполняется за один
  проход по шаблону: текст аргумента (например, имя макроса вида `{1}`)
  больше не может «раскрыться» как плейсхолдер.
- В метаданных workspace прописан актуальный `repository`.
- Отпечаток экрана усилен средним цветом области: однотонные области
  разного цвета (например, красная кнопка вместо синей), неразличимые для
  average hash, теперь корректно останавливают воспроизведение. Старые
  отпечатки (голое число в JSON) продолжают загружаться.

Текущее состояние: **88 тестов (67 ядро + 15 GUI + 6 CLI)** в базовой сборке
(`cargo test --workspace`), плюс ещё 16 под фичами `evdev`/`portal-hotkeys`
(14 в ядре + 2 в GUI — не входят в число выше, гоняются отдельным шагом CI
только на Linux, см. "Тесты"). CI (fmt + clippy + тесты трёх платформ +
release-сборки) зелёный.

### За рамками MVP (сделано позже)

- **Индекс списка макросов** — список читает сводки из `index.json` (кэша),
  не парсит тела макросов с превью; индекс отсутствует/побит — молча
  перестраивается сканированием.
- **CLI-крейт** — headless-проигрывание макроса из файла с управлением
  скоростью и режимом повтора.
